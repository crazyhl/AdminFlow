## 技术决策

- 后端：PHP + Laravel，当前以 Laravel 13.x 为基线；模块化单体。
- 数据库：MySQL 8.4 系列、InnoDB、utf8mb4；只支持这一种业务数据库，不开发双数据库兼容层。
- 页面：Laravel Blade 服务端渲染，htmx 按需提供局部更新，少量 JavaScript 处理本地交互；不采用 Vue、Nuxt、Element Plus 或前后端分离架构。
- 页面导航优先使用普通链接；列表筛选、分页和表单提交按需要使用 htmx，不以全站 SPA 化为目标。不为当前网页额外建设一套 JSON API。
- 后台样式优先采用 Tailwind CSS 技术栈；具体 UI 组件库、后台模板及交互扩展框架待后续讨论确定，本次不指定具体产品或新增依赖。优先复用兼容 Blade 与 htmx 的成熟样式或组件，只封装当前页面需要的 Blade 组件，不自建通用后台框架或完整组件库。
- 认证：Laravel 同源 Web 路由、Cookie 会话和 CSRF 中间件；普通表单及 htmx 写请求均受保护，不因局部更新绕过认证或授权。
- PHP 运行：FrankenPHP 常规模式；本阶段不启用 Octane/Swoole 常驻应用模式。
- 本地运行：Docker Compose。常驻服务仅包含当前必需的 PHP、MySQL；如使用 Vite，Node 仅用于开发和静态资源构建，生产不运行 Node 服务。
- Redis、队列、Flowable 是后续既定方向，本阶段不接入；生成器、模板前台本阶段不实现。
- 依赖与镜像固定实际版本/摘要，不能使用不受控的 latest。

## 本次选型调整与影响（2026-10-27）

- 用户明确选择减少前端复杂度，使用 Laravel + Blade + htmx 替换 Laravel API + Nuxt/Vue + Element Plus。业务范围、数据模型、权限规则和事务要求不变，没有新增业务任务。
- P1-01 的前后端工程及 API 封装工作替换为 Blade 布局、最小组件和统一局部响应约定；P1-05 的前端类型检查替换为页面与交互验证，以及适用时的静态资源构建检查。
- 去掉 Element Plus 后，后台布局、表单、表格和反馈组件需要选型、适配和维护。AI 可协助实现，但不据此假定完整后台组件体系成本很低；当前仅交付 P1 所需的最小界面。
- 后续复杂表格、拖拽或流程设计器按实际需求单独评估 JavaScript 组件集成，不提前纳入本阶段。部署规划同步去掉 Nuxt 服务，部署实施仍在 P1 验收后安排。

## 唯一目标

实现两个租户下的登录、最小角色权限和采购申请草稿 CRUD，用真实接口及页面验证租户隔离与授权。第一阶段不包含采购审批，也不模拟工作流。

## 任务与顺序

### P1-01：工程骨架

- 建立 Laravel 单体工程，集成 Blade 与 htmx，统一启动说明。
- 建立 Platform（租户/身份/权限）与 Procurement（采购申请）两个模块目录及明确调用边界。
- 统一完整页面与 HTML 片段响应、分页、请求校验和提示方式；明确 422 校验错误、409 版本冲突、403 权限不足、会话失效及 CSRF 失效的页面行为。htmx 错误状态响应须显式配置渲染或跳转处理，避免默认不替换而没有用户反馈。
- Migration + Seeder 初始化两个租户与测试账号。
- 建立最小登录页、后台布局和采购列表占位页。
- 不开发通用插件加载器、可视化配置器或生成器。

### P1-02：认证与租户上下文

- 登录、退出、当前用户与当前租户信息。
- 用户是身份，tenant_user 是租户成员关系；本阶段每个演示用户仅需一个成员关系，不提供租户切换页面。
- 租户标识可参与登录定位，但每次业务请求的租户上下文必须由服务器根据已认证且有效的成员关系确定。
- 不允许通过提交 tenant_id、记录 ID 或角色 ID访问其他租户。
- 平台侧租户创建使用 Seeder；不建设平台运营后台。

### P1-03：最小用户与权限

- 两个固定租户角色：admin、member；权限标识和角色初始授权通过 Seeder 固定。
- admin：查看本租户所有采购草稿，管理本租户成员；只编辑、删除自己创建的采购草稿。
- member：仅查看、创建、编辑、删除自己的采购草稿。
- 租户管理员可创建本租户用户/成员、分配上述固定角色、停用成员。
- 创建身份、成员关系和角色关联作为事务提交；关联角色必须属于同一租户。
- 角色修改和成员停用在下一次受保护请求中生效，本阶段直接查库，不加权限缓存。
- 不实现角色 CRUD、权限编辑器、动态菜单、部门、岗位、部门数据权限。

### P1-04：采购申请草稿

- 固定字段：id、tenant_id、created_by（用户 ID）、title、amount、purpose、version、created_at、updated_at。
- 金额用 DECIMAL，不使用浮点数；version 用于乐观锁。
- 新建、列表、详情、编辑、删除；只处理草稿，无审批状态转换。
- 列表提供标题筛选、分页和稳定排序；所有入口执行相同租户及数据范围规则。
- created_by 和 tenant_id 由服务器赋值，客户端不得指定或修改。
- 编辑时携带预期 version，更新条件包含版本；冲突明确返回 409，避免静默覆盖。
- Blade 与 htmx 实现对应页面、请求校验提示与权限反馈，服务器始终独立授权；完整页面和片段请求执行相同的业务规则。
- 删除范围限于上述可删除的草稿，删除也校验预期版本。
- 不实现采购明细、库存、预算、供应商、附件、提交审批、支付。

### P1-05：验证与交付

- 自动化测试验证跨租户列表/详情/创建/修改/删除、越权角色关联、成员停用、角色变更、事务回滚和版本冲突。
- 数据库行为测试使用 MySQL，不只依靠 SQLite 替代数据库。
- 验证浏览器 Cookie 登录及 CSRF 流程，覆盖普通表单及 htmx 请求；验证完整页面、筛选分页、校验错误、权限反馈、版本冲突和会话失效。静态资源如使用构建工具，构建必须通过；不再要求 Vue/TypeScript 类型检查。
- Migration + Seeder 可以从空库初始化完整演示环境。
- README 提供启动、测试、演示账号与演示流程。
- 人工演示 A/B 租户与 admin/member 权限差异，确认页面和实际接口一致。
- 不加入压测平台或承诺未经测量的性能指标。

## 完成标准

1. 两个租户账号都能正常登录、退出。
2. member 完成自己的采购草稿 CRUD。
3. admin 看见本租户全部草稿；无法修改其他成员的草稿。
4. 猜测其他租户记录 ID、提交其他 tenant_id 或角色 ID 都不能越权。
5. 停用和权限变更下一次请求生效。
6. 创建成员的多表操作失败时完整回滚。
7. 两次编辑同一版本，后提交者收到明确冲突，不覆盖先提交的数据。
8. 从空库初始化、自动化测试、页面与交互检查、适用时的静态资源构建和人工演示均通过。

## 本阶段参考数据表

- tenants：租户。
- users：用户身份。
- tenant_user：租户成员关系与成员状态。
- roles：租户内固定角色，唯一键 (tenant_id, code)。
- permissions：代码定义的权限目录。
- tenant_user_role：成员角色关联。
- role_permission：角色权限关联。
- purchase_requests：采购草稿。
- Laravel 会话等技术表按框架需要创建。

成员关系唯一键 (tenant_id, user_id)。关联角色、成员与采购数据的租户一致性必须校验，能够由数据库约束保障的同时设置约束。业务检索根据查询形态建立包含 tenant_id 的索引；不把全部业务字段放进 JSON。

## 数据库选型依据

- 当前功能由关系表、事务、唯一约束、索引与少量配置数据组成，MySQL 已满足需求；延续现有选型，减少无明确收益的变动。
- PostgreSQL 的 JSONB 与行级安全有价值，但当前不依赖它们。数据库行级安全也不替代业务操作授权，且需要正确配置数据库角色与连接上下文。

- https://dev.mysql.com/doc/refman/8.4/en/json.html
